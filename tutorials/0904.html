Building a Streaming Chat UI

Learn about building a streaming chat ui.

What Is Streaming and Why Does It Matter?

When you interact with most AI chatbots today, you've probably noticed that the response doesn't appear all at once. Instead, words seem to flow in one by one, like someone is typing in real time. This behavior is called streaming, and it fundamentally changes how users experience AI applications. Rather than staring at a blank screen waiting for a complete response to arrive in one big chunk, users see progress happening in front of them, which makes the experience feel faster, more natural, and more engaging.

From a technical perspective, streaming means that the server sends the AI's response piece by piece — often token by token — as it is being generated, rather than waiting for the entire response to be finished before sending anything back to the client. This requires a different approach to how we build both our backend API and our frontend user interface. In this lesson, you'll learn exactly how to build a streaming chat UI from the ground up.

New to AI concepts? A token is the basic unit of text that an AI model processes. A token can be a word, part of a word, or even a single character depending on the model. When we say the AI generates text "token by token," we mean it predicts the next small piece of text, then the next, and so on, building up a full response incrementally.

How Streaming Works Under the Hood

To understand streaming, let's break down what happens in a typical non-streaming (batch) request versus a streaming request.

The Non-Streaming (Batch) Flow

  1. The user types a message and hits send.
  2. The frontend sends an HTTP POST request to the backend with the user's message.
  3. The backend sends the message to the AI model and waits for the entire response to be generated.
  4. Once the full response is ready, the backend sends it back as a single JSON payload.
  5. The frontend receives the complete response and displays it all at once.

For a response that takes 10 seconds to generate, the user sees absolutely nothing for 10 full seconds. That's a poor user experience.

The Streaming Flow

  1. The user types a message and hits send.
  2. The frontend sends an HTTP POST request to the backend with the user's message (and often a special header or parameter indicating the client wants a stream).
  3. The backend begins sending the AI model's response as it is generated, sending small chunks of text over a persistent connection.
  4. Each chunk arrives at the frontend and is immediately appended to the displayed response.
  5. The connection closes when the AI model signals it has finished generating.
Analogy: Think of streaming like a live sports broadcast versus receiving a recorded highlight reel. With streaming, you watch the action unfold in real time. Without streaming, you wait until the entire game is over before you get a summary. Both give you the same final content, but the experience is completely different.

Building the Streaming Backend

Let's start by building a FastAPI backend that supports streaming responses. We'll use Server-Sent Events (SSE), which is the most common protocol for streaming from a server to a browser.

Setting Up the FastAPI Project

First, make sure you have the required packages installed:

pip install fastapi uvicorn openai

Now let's create a simple FastAPI application that simulates an AI agent responding with a streaming response:

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio
import json
import time

app = FastAPI()


async def fake_ai_stream(user_message: str):
    """
    Simulates an AI model that generates a response token by token.
    In a real application, you would call an actual AI model API here.
    """
    # A sample response we'll stream out word by word
    response_text = (
        "Great question! Building a streaming chat UI involves "
        "two main parts: a backend that sends data incrementally, "
        "and a frontend that displays it as it arrives. "
        "Let me walk you through both."
    )

    # Split the response into individual words to simulate tokens
    tokens = response_text.split()

    for token in tokens:
        # Simulate the delay between tokens (as a real AI model would have)
        await asyncio.sleep(0.15)

        # Create a JSON payload for each chunk
        chunk = json.dumps({"token": token + " "})

        # Yield in SSE format: "data: {json}\n\n"
        yield f"data: {chunk}\n\n"

    # Send a final [DONE] message to signal completion
    yield "data: [DONE]\n\n"


@app.post("/chat")
async def chat(user_message: str):
    """
    Endpoint that accepts a user message and returns a streaming response.
    """
    return StreamingResponse(
        fake_ai_stream(user_message),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # Disable buffering in nginx if used
        }
    )


if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)

Let's break down the key parts of this code:

  • StreamingResponse — This is FastAPI's way of telling the client, "I'm going to keep this connection open and send data over time." It wraps our generator function.
  • media_type="text/event-stream" — This tells the browser to interpret the incoming data as Server-Sent Events, which the browser has built-in support for via the EventSource API.
  • The yield keyword — Our fake_ai_stream function is a generator. Each yield statement sends one chunk of data to the client. The function pauses between chunks (simulated with asyncio.sleep), just like a real AI model takes time between generating tokens.
  • SSE format — Each chunk must follow the format data: {content}\n\n. The double newline signals the end of one event.
  • [DONE] signal — This is a convention (popularized by OpenAI) that tells the client the stream is complete.
Important: Make sure your deployment setup supports streaming. Some platforms (like certain serverless environments) buffer the entire response before sending it, which breaks streaming. If you're testing locally with Uvicorn, you're fine. For production, check your hosting provider's documentation.

Connecting to a Real AI Model

In practice, you'd replace the fake_ai_stream generator with a call to an actual AI API that supports streaming. Here's how you'd do it with OpenAI's API:

import openai

client = openai.AsyncOpenAI(api_key="your-api-key-here")


async def openai_stream(user_message: str):
    """
    Streams a response from OpenAI's API token by token.
    """
    stream = await client.chat.completions.create(
        model="gpt-4o",
        messages=[
            {"role": "system", "content": "You are a helpful AI assistant."},
            {"role": "user", "content": user_message}
        ],
        stream=True  # This is the key parameter!
    )

    async for chunk in stream:
        if chunk.choices[0].delta.content is not None:
            content = chunk.choices[0].delta.content
            data = json.dumps({"token": content})
            yield f"data: {data}\n\n"

    yield "data: [DONE]\n\n"

The critical parameter here is stream=True. Without it, the OpenAI API waits for the full response before returning. With it, the API returns a stream object that yields chunks as they're generated.

Building the Streaming Frontend

Now let's build the chat UI that receives and displays the streaming response. We'll use vanilla JavaScript with the fetch API, which supports streaming responses natively via ReadableStream.

Understanding the Client-Side Approach

There are two main approaches to consuming a streaming response on the frontend:

Approach Pros Cons Best For
EventSource Simple API, automatic reconnection GET requests only, no custom headers Simple streaming where you control the URL
Fetch + ReadableStream Supports POST, custom headers, full control Slightly more code to write Chat applications (you need POST to send messages)

For our chat UI, we'll use Fetch + ReadableStream because we need to send the user's message in a POST request body.

                                console.error('Failed to parse chunk:', data);

                    }

This might look like a lot of code, but the core streaming logic is actually quite elegant. Let's walk through the most important parts:

Breaking Down the Streaming Logic

The key to understanding the frontend is this section inside sendMessage():

// Get a reader from the response body stream
const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = '';

while (true) {
    const { done, value } = await reader.read();

    if (done) break;

    buffer += decoder.decode(value, { stream: true });

    const lines = buffer.split('\n\n');
    buffer = lines.pop(); // Keep incomplete chunk

    for (const line of lines) {
        if (line.startsWith('data: ')) {
            const data = line.replace('data: ', '');

            if (data === '[DONE]') {
                assistantMsg.classList.remove('streaming');
                break;
            }

            const parsed = JSON.parse(data);
            if (parsed.token) {
                assistantMsg.textContent += parsed.token;
            }
        }
    }
}

Here's what's happening step by step:

  1. response.body.getReader() — The response.body of a fetch request is a ReadableStream. Calling .getReader() gives us a reader object that lets us pull chunks of data from the stream one at a time.
  2. reader.read() — Each call returns a promise that resolves with { done, value }. done is true when the stream is finished. value is a Uint8Array containing the raw bytes of the next chunk.
  3. TextDecoder — Converts the raw bytes into a string.
  4. Buffer management — A single chunk from the stream might contain a partial SSE message. We maintain a buffer variable to accumulate data and only process complete messages (those terminated by \n\n). Any leftover partial message stays in the buffer for the next iteration.
  5. Appending tokens — Each parsed token is immediately appended to the assistant's message element, causing the text to appear token by token on screen.
Pro tip: The blinking cursor effect (the ::after pseudo-element with the ▊ character) is a small touch that makes the streaming feel much more polished. Users instinctively recognize a blinking cursor as "something is being typed," which improves perceived responsiveness.

Handling Edge Cases and Errors

Real-world streaming chat UIs need to handle several edge cases that our basic implementation doesn't cover yet. Let's discuss the most important ones.

Network Failures Mid-Stream

What happens if the user's internet connection drops while the AI is halfway through generating a response? The reader.read() call will throw an error. Our current try/catch block handles this, but we could do better by:

  • Showing a specific "Connection lost" indicator.
  • Offering a retry button that re-sends the last message.
  • Preserving the partial response that was received before the failure.

Stopping a Stream Early

Sometimes users want to stop the AI mid-response. This is especially useful when the AI is generating a long answer and the user realizes it's going in the wrong direction. You can implement this using an AbortController:

let currentController = null;

async function sendMessage() {
    // Cancel any existing stream
    if (currentController) {
        currentController.abort();
    }

    currentController = new AbortController();

    try {
        const response = await fetch('/chat?user_message=' + encodeURIComponent(text), {
            method: 'POST',
            signal: currentController.signal,  // Pass the abort signal
        });

        // ... rest of streaming logic ...

    } catch (error) {
        if (error.name === 'AbortError') {
            console.log('Stream was cancelled by user');
            assistantMsg.classList.remove('streaming');
        } else {
            // Handle real errors
            assistantMsg.textContent = 'An error occurred.';
            assistantMsg.classList.remove('streaming');
        }
    }
}

function stopStreaming() {
    if (currentController) {
        currentController.abort();
        currentController = null;
    }
}

Rate Limiting and Backpressure

If your AI model generates tokens faster than the network can deliver them, you might run into backpressure issues. In most browser-to-server scenarios, this isn't a problem because the network is the bottleneck, not the AI. However, if you're building a high-traffic application, consider:

  • Implementing rate limiting on the backend to prevent abuse.
  • Using a message queue (like Redis) to manage concurrent streams.
  • Setting a maximum token limit per response to prevent extremely long streams.
Security note: Never expose your AI API keys in frontend code. Always route requests through your own backend server, which holds the API keys securely. The frontend should only communicate with your backend, not directly with the AI provider.

Enhancing the User Experience

Once you have basic streaming working, there are several enhancements that can make your chat UI feel truly polished.

Markdown Rendering

AI models often respond with Markdown formatting (bold, italic, code blocks, lists). To render this properly, you'll need a Markdown parser on the frontend. A popular choice is marked.js:

<script src="https://cdn.jsdelivr.net/npm/marked/marked.min.js"></script>

// Instead of:
assistantMsg.textContent += parsed.token;

// Use:
assistantMsg.innerHTML = marked.parse(assistantMsg.textContent + parsed.token);

However, be cautious about XSS (Cross-Site Scripting) vulnerabilities when using innerHTML. Make sure to sanitize the HTML output using a library like DOMPurify:

<script src="https://cdn.jsdelivr.net/npm/dompurify@3.0.6/dist/purify.min.js"></script>

assistantMsg.innerHTML = DOMPurify.sanitize(
    marked.parse(assistantMsg.textContent + parsed.token)
);

Message History and Persistence

For a production chat UI, you'll want to:

  • Store conversation history in a database so users can return to previous conversations.
  • Send the full conversation history with each new message so the AI has context.
  • Display previous messages when the page loads by fetching them from your backend.

Typing Indicators

Before the first token arrives, show a brief "AI is thinking..." indicator. This bridges the gap between the user sending a message and the first token appearing:

function showTypingIndicator() {
    const indicator = document.createElement('div');
    indicator.classList.add('message', 'assistant', 'typing-indicator');
    indicator.id = 'typing-indicator';
    indicator.textContent = 'AI is thinking...';
    messagesContainer.appendChild(indicator);
    messagesContainer.scrollTop = messagesContainer.scrollHeight;
}

function removeTypingIndicator() {
    const indicator = document.getElementById('typing-indicator');
    if (indicator) indicator.remove();
}

Coding Exercise

Exercise: Add a Stop Button

Modify the chat UI code from this lesson to add a "Stop" button that appears while a response is being streamed. When clicked, it should abort the current stream using an AbortController and change the button back to "Send".

Your solution should:

  • Replace the "Send" button with a "Stop" button while streaming is in progress.
  • Use AbortController to cancel the fetch request when "Stop" is clicked.
  • Handle the AbortError gracefully (don't show an error message — the user intentionally stopped the stream).
  • Restore the "Send" button after the stream is stopped or completes.

Here's the key modifications needed. First, update the HTML for the button:

<button id="send-btn" onclick="handleButtonClick()">Send</button>

Then add the JavaScript logic:

let currentController = null;
let isStreaming = false;

function handleButtonClick() {
    if (isStreaming) {
        stopStreaming();
    } else {
        sendMessage();
    }
}

async function sendMessage() {
    const text = userInput.value.trim();
    if (!text) return;

    userInput.value = '';
    userInput.disabled = true;

    // Switch to Stop button
    isStreaming = true;
    sendBtn.textContent = 'Stop';
    sendBtn.style.background = '#e74c3c';

    addMessage('user', text);
    const assistantMsg = addMessage('assistant', '');
    assistantMsg.classList.add('streaming');

    // Create a new AbortController for this request
    currentController = new AbortController();

    try {
        const response = await fetch('/chat?user_message=' + encodeURIComponent(text), {
            method: 'POST',
            signal: currentController.signal,
        });

        const reader = response.body.getReader();
        const decoder = new TextDecoder();
        let buffer = '';

        while (true) {
            const { done, value } = await reader.read();
            if (done) break;

            buffer += decoder.decode(value, { stream: true });
            const lines = buffer.split('\n\n');
            buffer = lines.pop();

            for (const line of lines) {
                if (line.startsWith('data: ')) {
                    const data = line.replace('data: ', '');
                    if (data === '[DONE]') {
                        assistantMsg.classList.remove('streaming');
                        break;
                    }
                    try {
                        const parsed = JSON.parse(data);
                        if (parsed.token) {
                            assistantMsg.textContent += parsed.token;
                            messagesContainer.scrollTop = messagesContainer.scrollHeight;
                        }
                    } catch (e) {
                        console.error('Parse error:', data);
                    }
                }
            }
        }
    } catch (error) {
        if (error.name === 'AbortError') {
            // User stopped the stream — this is expected, not an error
            assistantMsg.classList.remove('streaming');
            assistantMsg.textContent += ' [stopped]';
        } else {
            assistantMsg.textContent = 'An error occurred. Please try again.';
            assistantMsg.classList.remove('streaming');
        }
    } finally {
        // Reset UI state
        isStreaming = false;
        sendBtn.textContent = 'Send';
        sendBtn.style.background = '#4a6cf7';
        currentController = null;
        userInput.disabled = false;
        userInput.focus();
    }
}

function stopStreaming() {
    if (currentController) {
        currentController.abort();
    }
}

The key insight is using a shared isStreaming state variable to toggle the button between "Send" and "Stop" modes, and passing the AbortController.signal to the fetch() call so the stream can be cancelled on demand.

Key Takeaways

  • Streaming improves user experience by showing AI responses incrementally rather than making users wait for the complete response.
  • Server-Sent Events (SSE) is the standard protocol for streaming from server to browser, using the text/event-stream content type and the data: {json}\n\n format.
  • FastAPI's StreamingResponse wraps an async generator to send chunks over time, keeping the HTTP connection open.
  • The Fetch API's ReadableStream interface lets you read streaming responses on the frontend using getReader() and a read() loop.
  • Buffer management is critical on the frontend — a single network chunk may contain partial SSE messages, so you need to accumulate data and only process complete messages.
  • AbortController allows users to cancel an in-progress stream, which is essential for a good chat UX.
  • Always route AI API calls through your backend — never expose API keys in frontend code.
  • Enhancements like Markdown rendering, typing indicators, and message persistence take a basic streaming chat from functional to polished.
