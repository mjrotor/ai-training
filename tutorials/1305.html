Production Vector DB Patterns

Learn about production vector db patterns.

Why Vector Databases in Production?

So far, you've experimented with vector databases in notebooks and small scripts. But when you move to production — serving real users, handling real traffic, and managing real data — everything changes. A production vector database setup needs to handle millions of embeddings, serve queries in under 100ms, and stay reliable even when things break.

In this lesson, we'll walk through the patterns and practices that separate a toy project from a production-grade vector search system.

What you'll learn: How to design, deploy, and maintain vector databases in production environments — including indexing strategies, hybrid search, filtering, monitoring, and scaling.

Choosing the Right Vector Database

Not all vector databases are created equal. Your choice depends on your scale, latency requirements, and whether you need managed infrastructure or self-hosting.

Database Best For Deployment Max Scale (approx.)
Pinecone Serverless, zero-ops Fully managed Billions of vectors
Weaviate Hybrid search + GraphQL Self-hosted or cloud Hundreds of millions
Qdrant High performance, filtering Self-hosted or cloud Billions of vectors
pgvector Existing PostgreSQL users Self-hosted Tens of millions
Milvus Large-scale, GPU-accelerated Self-hosted or cloud Billions of vectors
Tip: If you're already running PostgreSQL, pgvector is the fastest path to production. You avoid managing a separate service and can combine vector search with traditional SQL queries.

Indexing Strategies for Production

When you have millions of vectors, a brute-force search (comparing the query to every single vector) is far too slow. That's where approximate nearest neighbor (ANN) indexes come in. They trade a tiny bit of accuracy for massive speed gains.

Common ANN Index Types

  • HNSW (Hierarchical Navigable Small World): The most popular choice. Great recall, fast queries, but uses more memory. Default in most databases.
  • IVF (Inverted File Index): Partitions vectors into clusters. Faster indexing, slightly lower recall. Good for very large datasets.
  • ScaNN (Google): Optimized for billion-scale datasets. Uses anisotropic vector quantization.
  • DiskANN: Designed for datasets that don't fit in RAM. Stores index on SSD.

Configuring HNSW in Qdrant

from qdrant_client import QdrantClient
from qdrant_client.http.models import Distance, VectorParams

client = QdrantClient(url="http://localhost:6333")

# Create collection with HNSW index
client.create_collection(
    collection_name="production_docs",
    vectors_config=VectorParams(
        size=768,          # embedding dimension
        distance=Distance.COSINE
    ),
    hnsw_config={
        "m": 16,           # number of edges per node (higher = more accurate, more memory)
        "ef_construct": 200  # search width during index build
    }
)

print("Collection created with HNSW index")
Warning: Higher m and ef_construct values improve recall but increase memory usage and indexing time. For production, start with m=16 and ef_construct=200, then tune based on your latency and accuracy requirements.

Hybrid Search: Combining Vector and Keyword Matching

Pure vector search is powerful, but it sometimes misses exact keyword matches. Hybrid search combines semantic similarity with traditional keyword matching (BM25) for the best of both worlds.

How Hybrid Search Works

  1. The query is converted to an embedding for vector search
  2. The same query is analyzed for keyword matching (BM25/TF-IDF)
  3. Results from both methods are merged using a reciprocal rank fusion or weighted scoring

import numpy as np

def reciprocal_rank_fusion(results_list, k=60):
    """
    Merge multiple ranked result lists using Reciprocal Rank Fusion.
    results_list: list of lists, each containing (doc_id, score) tuples
    """
    fused_scores = {}
    
    for results in results_list:
        for rank, (doc_id, _) in enumerate(results):
            if doc_id not in fused_scores:
                fused_scores[doc_id] = 0
            fused_scores[doc_id] += 1.0 / (k + rank + 1)
    
    # Sort by fused score descending
    ranked = sorted(fused_scores.items(), key=lambda x: x[1], reverse=True)
    return ranked

# Example: merging vector search results with BM25 results
vector_results = [("doc_42", 0.95), ("doc_17", 0.89), ("doc_88", 0.82)]
bm25_results = [("doc_17", 12.4), ("doc_55", 11.1), ("doc_42", 9.8)]

fused = reciprocal_rank_fusion([vector_results, bm25_results])
print("Hybrid ranking:", fused)
# Output: [('doc_17', 0.0328), ('doc_42', 0.0325), ('doc_55', 0.0164), ('doc_88', 0.0161)]
Tip: Weaviate and Elasticsearch both support hybrid search natively. If you're using Qdrant or Pinecone, you'll need to implement the fusion logic yourself (as shown above) or use a library like ragas for evaluation.

Metadata Filtering in Production

In real applications, you rarely want to search across all your data. You need to filter by date, category, user permissions, or other metadata. This is where pre-filtering and post-filtering strategies matter.

Pre-filtering vs Post-filtering

Strategy How it works Pros Cons
Pre-filtering Filter candidates first, then search vectors Fast for selective filters Can miss relevant results outside filter
Post-filtering Search vectors first, then filter results Never misses relevant results Slow if filter eliminates many results
Payload indexing Database indexes metadata fields Best of both worlds Extra memory and setup

Filtering with Qdrant


from qdrant_client.http.models import Filter, FieldCondition, MatchValue

# Create payload indexes for fields you'll filter on

    collection_name="production_docs",
    field_name="category",
    field_schema="keyword"
)

client.create_payload_index(
    collection_name="production_docs",
    field_name="created_at",
    field_schema="datetime"
)

# Search with metadata filter
search_result = client.search(
    collection_name="production_docs",
    query_vector=query_embedding,
    query_filter=Filter(
        must=[
            FieldCondition(
                key="category",
                match=MatchValue(value="engineering")
            ),
            FieldCondition(
                key="created_at",
                range={
                    "gte": "2024-01-01T00:00:00Z"
                }
            )
        ]
    ),
    limit=10
)

for hit in search_result:
    print(f"ID: {hit.id}, Score: {hit.score:.3f}, Category: {hit.payload['category']}")

Batching and Ingestion Pipelines

In production, you don't insert one vector at a time. You need a robust ingestion pipeline that can handle bulk updates, failures, and re-processing.

Building a Resilient Ingestion Pipeline


import time
from typing import List, Dict, Any

class VectorIngestionPipeline:
    def __init__(self, client, collection_name: str, batch_size: int = 256):
        self.client = client
        self.collection_name = collection_name
        self.batch_size = batch_size
        self.failed_batches = []
    
    def ingest(self, documents: List[Dict[str, Any]], embeddings: List[List[float]]):
        """
        Ingest documents with retry logic and progress tracking.
        """
        total = len(documents)
        inserted = 0
        
        for i in range(0, total, self.batch_size):
            batch_docs = documents[i:i + self.batch_size]
            batch_vecs = embeddings[i:i + self.batch_size]
            
            try:
                self._upsert_batch(batch_docs, batch_vecs)
                inserted += len(batch_docs)
                print(f"Progress: {inserted}/{total} ({100*inserted/total:.1f}%)")
                
            except Exception as e:
                print(f"Error at batch {i}: {e}")
                self.failed_batches.append((i, batch_docs, batch_vecs))
                time.sleep(1)  # brief pause before retry
        
        # Retry failed batches
        if self.failed_batches:
            print(f"\nRetrying {len(self.failed_batches)} failed batches...")
            self._retry_failed()
        
        print(f"Done! Inserted {inserted} documents.")
    
    def _upsert_batch(self, docs, vectors):
        points = [
            {
                "id": doc["id"],
                "vector": vec,
                "payload": {k: v for k, v in doc.items() if k != "id"}
            }
            for doc, vec in zip(docs, vectors)
        ]
        self.client.upsert(
            collection_name=self.collection_name,
            points=points,
            wait=True
        )
    
    def _retry_failed(self):
        for idx, docs, vecs in self.failed_batches:
            try:
                self._upsert_batch(docs, vecs)
                print(f"  Retry succeeded for batch {idx}")
            except Exception as e:
                print(f"  Retry failed for batch {idx}: {e}")
        self.failed_batches.clear()

# Usage
pipeline = VectorIngestionPipeline(client, "production_docs", batch_size=512)
pipeline.ingest(documents, embeddings)
Production tip: For very large datasets (100M+ vectors), consider using your database's native bulk import tools. Qdrant has qdrant-local for offline indexing, and Pinecone supports upsert via REST API with parallel workers.

Monitoring and Observability

A production vector search system without monitoring is a ticking time bomb. You need to track latency, recall, index health, and resource usage.

Key Metrics to Track

  • p50 / p95 / p99 query latency: How fast are your searches? p99 matters most for user experience.
  • Recall@K: Of the true top-K nearest neighbors, how many did your ANN index return?
  • Index size and memory usage: Is your index growing beyond available RAM?
  • Ingestion throughput: Vectors per second — are you keeping up with new data?
  • Error rate: Failed queries, timeouts, connection drops.

Measuring Recall in Production


import numpy as np

def measure_recall(
    client,
    collection_name: str,
    test_queries: List[List[float]],
    ground_truth: List[List[int]],
    k: int = 10,
    ef_search: int = 128
) -> float:
    """
    Measure recall@K by comparing ANN results to ground truth.
    ground_truth: list of lists, each containing the true top-K doc IDs
    """
    recalls = []
    
    for query_vec, true_ids in zip(test_queries, ground_truth):
        # Get ANN results
        results = client.search(
            collection_name=collection_name,
            query_vector=query_vec,
            limit=k,
            search_params={"ef_search": ef_search}
        )
        retrieved_ids = set(hit.id for hit in results)
        true_set = set(true_ids[:k])
        
        # Calculate recall for this query
        if len(true_set) > 0:
            recall = len(retrieved_ids & true_set) / len(true_set)
            recalls.append(recall)
    
    avg_recall = np.mean(recalls)
    print(f"Recall@{k}: {avg_recall:.4f}")
    print(f"  Min: {min(recalls):.4f}, Max: {max(recalls):.4f}")
    return avg_recall

# Example usage
# avg = measure_recall(client, "production_docs", test_queries, ground_truth, k=10)
Warning: Recall degrades as your dataset grows or as your index parameters drift. Schedule regular recall evaluations — at least weekly for active systems — and set up alerts if recall drops below your threshold (typically 0.95 for most applications).

Caching Frequent Queries

In many applications, a small number of queries account for a large percentage of traffic. Caching these can dramatically reduce load on your vector database.


import hashlib
import json
from functools import lru_cache

class CachedVectorSearch:
    def __init__(self, client, collection_name: str, cache_size: int = 10000):
        self.client = client
        self.collection_name = collection_name
        self._cache = {}
        self._cache_order = []
        self.cache_size = cache_size
    
    def _cache_key(self, query_vector: list, filters: dict = None, top_k: int = 10) -> str:
        """Create a deterministic cache key from query parameters."""
        key_data = {
            "vec_hash": hashlib.md5(
                str([round(v, 6) for v in query_vector]).encode()
            ).hexdigest(),
            "filters": filters,
            "top_k": top_k
        }
        return hashlib.sha256(
            json.dumps(key_data, sort_keys=True).encode()
        ).hexdigest()
    
    def search(self, query_vector: list, filters: dict = None, top_k: int = 10):
        cache_key = self._cache_key(query_vector, filters, top_k)
        
        # Check cache
        if cache_key in self._cache:
            return self._cache[cache_key]
        
        # Query the database
        from qdrant_client.http.models import Filter as QdrantFilter
        q_filter = None
        if filters:
            conditions = [
                {"key": k, "match": {"value": v}}
                for k, v in filters.items()
            ]
            q_filter = QdrantFilter(must=conditions)
        
        results = self.client.search(
            collection_name=self.collection_name,
            query_vector=query_vector,
            query_filter=q_filter,
            limit=top_k
        )
        
        # Store in cache (simple LRU eviction)
        if len(self._cache) >= self.cache_size:
            oldest = self._cache_order.pop(0)
            del self._cache[oldest]
        
        self._cache[cache_key] = results
        self._cache_order.append(cache_key)
        
        return results

# Usage
searcher = CachedVectorSearch(client, "production_docs", cache_size=50000)
results = searcher.search(query_embedding, filters={"category": "engineering"})

Scaling Strategies

As your data grows, you'll need to scale. Here are the three main strategies:

1. Vertical Scaling (Bigger Machines)

Upgrade to more RAM, faster SSDs, or GPU-accelerated instances. Simple but has hard limits. Works well up to ~100M vectors.

2. Horizontal Sharding

Split your data across multiple nodes. Each shard holds a subset of vectors. Queries are sent to all shards and results are merged.


# Conceptual sharding example
class ShardedVectorDB:
    def __init__(self, shard_urls: List[str]):
        self.shards = [QdrantClient(url=url) for url in shard_urls]
    
    def search(self, query_vector: list, top_k: int = 10):
        all_results = []
        for shard in self.shards:
            results = shard.search(
                collection_name="docs",
                query_vector=query_vector,
                limit=top_k
            )
            all_results.extend(results)
        
        # Merge and re-rank
        all_results.sort(key=lambda x: x.score, reverse=True)
        return all_results[:top_k]

3. Quantization

Reduce the precision of your vectors to save memory and speed up search. Options include scalar quantization (int8) and product quantization (PQ).

Tip: Start with HNSW + scalar quantization. It gives you 4-8x memory reduction with minimal recall loss. Only move to product quantization if you need even more compression.

Exercise: Design a Production Architecture

Exercise

You're building a RAG system for a company with 5 million documents, expecting 1,000 queries per second at peak. Users need results in under 200ms (p99). Documents are updated daily.

Design the architecture by answering:

  1. Which vector database would you choose and why?
  2. What indexing strategy would you use?
  3. How would you handle daily document updates?
  4. What caching strategy would you implement?

Sample solution:

  1. Qdrant (self-hosted) or Pinecone (managed). Qdrant gives you control and excellent filtering; Pinecone removes ops burden. Both handle 5M vectors easily and support HNSW.
  2. HNSW with m=16, ef_construct=200, and scalar quantization. This gives ~95%+ recall with fast query times. Set ef_search=128 at query time for the 200ms target.
  3. Daily batch re-indexing via a pipeline. Use the ingestion pipeline pattern from this lesson. For documents that changed, delete the old vector and upsert the new one. Run this as a nightly job or streaming update.
  4. Two-tier caching: (a) An in-memory LRU cache for the top 50,000 most frequent queries. (b) A Redis cache with 1-hour TTL for all queries. This should handle 60-80% of traffic without hitting the vector DB.

Key Takeaways

  • Choose your vector database based on scale and team. Managed options (Pinecone, Weaviate Cloud) reduce ops work; self-hosted (Qdrant, Milvus) gives more control.
  • HNSW is the default index for most production use cases. Tune m and ef_construct for your accuracy vs. memory tradeoff.
  • Hybrid search combines the best of semantic and keyword matching. Use reciprocal rank fusion to merge results from both methods.
  • Metadata filtering is essential for real applications. Index your payload fields and use pre-filtering when possible.
  • Build resilient ingestion pipelines with batching and retry logic. Never insert vectors one at a time in production.
  • Monitor recall, latency, and throughput continuously. Set up alerts for degradation before your users notice.
  • Caching can reduce vector DB load by 60-80%. Implement LRU or Redis caching for frequent queries.
  • Plan for scaling early. Sharding and quantization are your tools for handling growth beyond a single node.
