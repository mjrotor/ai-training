Why Agents Need RAG

Welcome to Phase 2! In the first phase, you learned how AI agents perceive their environment and make simple decisions. Now it's time to tackle one of the most important capabilities for building truly useful agents: Retrieval-Augmented Generation (RAG).

Think of it this way: an AI agent without RAG is like a student taking a closed-book exam. It can only answer based on what it memorized during training. An AI agent with RAG is like an open-book exam — it can look up relevant information before answering, leading to far more accurate, up-to-date, and grounded responses.

What Is RAG?

Retrieval-Augmented Generation is a technique where an AI model retrieves relevant documents or data from an external knowledge source before generating its answer. Instead of relying solely on its internal (and potentially outdated) training knowledge, the agent "looks things up" first, then uses that retrieved context to produce a well-informed response.

The RAG pipeline typically involves three key stages:

  1. Indexing — Documents are split into chunks and converted into vector embeddings (numerical representations) and stored in a vector database.
  2. Retrieval — When a user asks a question, the system searches the vector database for the most relevant chunks.
  3. Generation — The retrieved chunks are fed to the LLM as context, which then produces a grounded answer.
💡 Did You Know? RAG was introduced in a 2020 paper by researchers at Facebook AI Research (now Meta AI). It has since become one of the most widely adopted patterns for building production AI applications.

The Problem RAG Solves

Without RAG, large language models have several critical limitations when used inside agents:

Problem Without RAG With RAG
Hallucinations Model may fabricate facts confidently Answers grounded in retrieved documents
Outdated Knowledge Limited to training data cutoff date Can access up-to-date documents
Domain-Specific Knowledge No access to proprietary/private data Can search company docs, manuals, etc.
Traceability No source citations Can cite which documents were used
Token Limits Must fit all context in prompt Only relevant chunks are retrieved

How RAG Fits Into the Agent Architecture

In our agent framework, RAG acts as a tool that the agent can call. When the agent determines that a user's question requires external knowledge, it invokes the RAG tool, which searches the knowledge base and returns relevant context. The agent then uses that context to formulate its response.

from openai import OpenAI

client = OpenAI()

def retrieve_context(query: str, vector_store, top_k: int = 3) -> list[str]:
    """Search the vector store for relevant document chunks."""
    results = vector_store.similarity_search(query, k=top_k)
    return [doc.page_content for doc in results]

def ask_with_rag(question: str, vector_store) -> str:
    """Answer a question using retrieved context."""
    # Step 1: Retrieve relevant documents
    context_chunks = retrieve_context(question, vector_store)
    context_text = "\n\n".join(context_chunks)

    # Step 2: Build a prompt with the retrieved context
    prompt = f"""Answer the following question based ONLY on the context below.
If the context doesn't contain enough information, say so.

Context:
{context_text}

Question: {question}
Answer:"""

    # Step 3: Generate the answer
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}]
    )
    return response.choices[0].message.content

# Example usage
answer = ask_with_rag("What is our return policy?", vector_store)
print(answer)
🔧 Pro Tip: The quality of RAG depends heavily on how you chunk your documents. Too large, and you lose precision. Too small, and you lose context. A common starting point is 250–500 word chunks with 10–20% overlap between them.

Building a Simple Vector Store

To make RAG work, you need a place to store and search your document embeddings. Let's build a minimal vector store using chromadb:

import chromadb
from chromadb.utils import embedding_functions

# Initialize a persistent ChromaDB client
chroma_client = chromadb.PersistentClient(path="./my_vector_db")

# Use OpenAI's embedding model (or use a free alternative)
openai_ef = embedding_functions.OpenAIEmbeddingFunction(
    api_key="your-api-key",
    model_name="text-embedding-3-small"
)

# Create or get a collection
collection = chroma_client.get_or_create_collection(
    name="knowledge_base",
    embedding_function=openai_ef
)

# Add documents
documents = [
    "Our return policy allows returns within 30 days of purchase.",
    "Free shipping is available for orders over $50.",
    "Customer support is available Monday through Friday, 9am to 6pm EST.",
    "We offer a 1-year warranty on all electronic products.",
    "International shipping takes 7-14 business days."
]

collection.add(
    documents=documents,
    ids=["doc1", "doc2", "doc3", "doc4", "doc5"]
)

# Query the collection
results = collection.query(
    query_texts=["How long do I have to return an item?"],
    n_results=2
)

print(results["documents"][0])
# Output: ['Our return policy allows returns within 30 days of purchase.',
#          'We offer a 1-year warranty on all electronic products.']

Chunking Strategies

Before documents can be embedded and stored, they need to be split into manageable pieces. Here are the most common strategies:

  • Fixed-size chunking — Split text into chunks of N characters with optional overlap. Simple and fast.
  • Recursive chunking — Split by paragraphs, then sentences, then words. Preserves natural boundaries.
  • Semantic chunking — Use embeddings to detect topic shifts and split accordingly. Most accurate but slower.
  • Document-specific chunking — Custom logic for specific formats (e.g., splitting code by functions, Markdown by headers).
from langchain.text_splitter import RecursiveCharacterTextSplitter

# Create a recursive text splitter
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # Each chunk is ~500 characters
    chunk_overlap=50,      # 50 characters of overlap between chunks
    length_function=len,
    separators=["\n\n", "\n", ". ", " ", ""]
)

long_document = """
Your long document text goes here. It could be a company handbook,
a technical manual, a research paper, or any text that needs to
be broken into smaller pieces for the RAG pipeline.
"""

chunks = splitter.split_text(long_document)

print(f"Number of chunks: {len(chunks)}")
for i, chunk in enumerate(chunks):
    print(f"Chunk {i+1} ({len(chunk)} chars): {chunk[:80]}...")
⚠️ Watch Out: Don't set your chunk size too small! If chunks are too short, the embedding model won't have enough context to create meaningful representations, and retrieval quality will drop significantly.

Retrieval Quality: The Make-or-Break Factor

Having a vector store is only half the battle. The retrieval step determines whether the agent finds the right information. Here are key factors that affect retrieval quality:

  1. Embedding model quality — Better embeddings capture semantic meaning more accurately.
  2. Query formulation — Sometimes the user's raw query isn't ideal for retrieval. Consider query rewriting or expansion.
  3. Top-K selection — Retrieving too few results may miss relevant info; too many adds noise.
  4. Hybrid search — Combining vector (semantic) search with keyword (BM25) search often yields the best results.
def hybrid_search(query: str, collection, top_k: int = 5) -> list[str]:
    """Combine semantic and keyword-style search for better results."""
    # Semantic search via embeddings
    semantic_results = collection.query(
        query_texts=[query],
        n_results=top_k
    )

    # For a production system, you'd also run BM25 keyword search
    # and merge/rerank the results. Here's a simplified version:
    retrieved_docs = semantic_results["documents"][0]

    # Remove duplicates while preserving order
    seen = set()
    unique_docs = []
    for doc in retrieved_docs:
        if doc not in seen:
            seen.add(doc)
            unique_docs.append(doc)

    return unique_docs

# Usage
results = hybrid_search("return policy timeframe", collection)
for doc in results:
    print(f"  → {doc}")

When Should an Agent Use RAG?

Not every agent interaction requires RAG. Here's a decision framework:

Scenario Use RAG? Reason
General conversation ❌ No Wastes time and tokens
Answering company-specific questions ✅ Yes Needs internal knowledge
Current events or news ✅ Yes Training data is outdated
Creative writing ❌ No No factual grounding needed
Technical documentation lookup ✅ Yes Precision is critical
💡 Agent Design Pattern: A well-designed agent should decide for itself when to invoke RAG. In the next phase, you'll learn how to train or prompt agents to make this decision autonomously as part of their reasoning loop.

Common Pitfalls and How to Avoid Them

As you build RAG-powered agents, watch out for these common mistakes:

  • Garbage in, garbage out — If your source documents are poorly formatted or contain errors, RAG won't fix that. Clean your data first.
  • Ignoring metadata — Tag documents with source, date, and category. This enables filtering and improves retrieval precision.
  • Not evaluating — Always measure retrieval precision and answer accuracy. Use test queries and expected answers to benchmark your system.
  • Over-relying on RAG — Some tasks (math, reasoning, code generation) don't benefit from retrieval. Know when to skip it.
🧪 Exercise: Build a RAG-Enhanced Agent Tool

Create a rag_tool function that an agent can call. The function should:

  1. Accept a user query and a list of knowledge base documents (strings).
  2. Simple keyword matching: find the document(s) with the most overlapping words with the query.
  3. Return the top matching document as context.
  4. Handle the case where no document matches (return a helpful message).

Bonus: Add a minimum relevance score threshold so low-quality matches are filtered out.

def rag_tool(query: str, documents: list[str], top_k: int = 1,
              min_score: float = 0.1) -> str:
    """
    A simple keyword-based RAG tool for an agent.
    In production, you'd use embeddings — this is a learning exercise!
    """
    query_words = set(query.lower().split())

    scored_docs = []
    for doc in documents:
        doc_words = set(doc.lower().split())
        # Simple Jaccard-like overlap score
        overlap = len(query_words & doc_words)
        score = overlap / max(len(query_words), 1)
        scored_docs.append((score, doc))

    # Sort by score descending
    scored_docs.sort(key=lambda x: x[0], reverse=True)

    # Filter by minimum threshold
    relevant = [(s, d) for s, d in scored_docs if s >= min_score]

    if not relevant:
        return "No relevant documents found in the knowledge base."

    # Return top_k results
    top_results = relevant[:top_k]
    context = "\n\n".join(
        f"[Relevance: {score:.2f}] {doc}"
        for score, doc in top_results
    )
    return context

# Test it
kb = [
    "Our return policy allows returns within 30 days.",
    "Free shipping on orders over $50.",
    "Warranty covers defects for 1 year from purchase."
]

print(rag_tool("How long can I return items?", kb))
# Output: [Relevance: 0.25] Our return policy allows returns within 30 days.

print(rag_tool("What is the weather today?", kb))
# Output: No relevant documents found in the knowledge base.

Key Takeaways

  • RAG = Retrieve + Generate: The agent looks up relevant documents before answering, leading to more accurate and grounded responses.
  • Three stages: Indexing (store embeddings), Retrieval (search for relevant chunks), Generation (LLM produces answer with context).
  • Chunking matters: How you split documents directly impacts retrieval quality. Start with recursive chunking at ~500 chars with overlap.
  • Not always needed: Agents should intelligently decide when to use RAG — not every query requires external knowledge.
  • Evaluate your system: Always benchmark retrieval precision and answer quality with test queries.
  • Hybrid search wins: Combining semantic (vector) search with keyword (BM25) search typically gives the best results.
