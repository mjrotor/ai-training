Running Evaluations

Learn about running evaluations.

What Are Evaluations?

Evaluations (or "evals") are structured tests that measure how well your AI agent performs at a given task. Instead of guessing whether your agent is working well, evaluations give you objective, repeatable measurements of quality. Think of them as a report card for your AI agent — they tell you exactly where your agent excels and where it needs improvement.

In the context of AI agents, evaluations typically test things like:

  • Accuracy: Did the agent produce the correct answer?
  • Tool use: Did the agent call the right tools with the right arguments?
  • Reasoning: Did the agent follow a logical chain of thought?
  • Safety: Did the agent avoid harmful or inappropriate outputs?
  • Latency: Did the agent respond within an acceptable time frame?
Why Evals Matter: Without evaluations, you are flying blind. You might deploy an agent that subtly degrades in quality over time. Evals catch regressions early and give you confidence that your agent meets a consistent standard before it reaches real users.

Types of Evaluations

There are several categories of evaluations you can run against an AI agent. Each type serves a different purpose and gives you a different perspective on agent quality.

1. Unit Evaluations

Unit evals test individual components of your agent in isolation. For example, you might test whether your prompt template correctly formats a date, or whether a single tool-calling function returns the expected structure. These are fast, deterministic, and easy to debug.

2. Integration Evaluations

Integration evals test how multiple components work together. For instance, you might evaluate whether the agent correctly chains a web search tool call with a summarization step. These tests are slower but catch issues that unit evals miss — like components that work individually but break when combined.

3. End-to-End Evaluations

End-to-end evals test the entire agent pipeline from user input to final output. These are the most realistic tests because they simulate actual user interactions. However, they are also the most expensive and time-consuming to run.

4. Human Evaluations

In some cases, automated metrics are not enough. Human evaluators review agent outputs and rate them on criteria like helpfulness, tone, and coherence. This is especially important for subjective tasks like creative writing or nuanced customer support.

Pro Tip: Start with unit evals early in development, add integration evals as your agent grows, and reserve end-to-end and human evals for pre-deployment validation. This layered approach saves time and money.

Designing an Evaluation Dataset

The foundation of any good evaluation is a well-designed dataset. Your eval dataset is a collection of test cases, each consisting of an input (what you feed the agent) and an expected output or behavior (what the agent should do).

Key Principles for Eval Datasets

  • Representative: Your test cases should mirror the real-world inputs your agent will encounter.
  • Diverse: Include edge cases, ambiguous queries, and adversarial inputs.
  • Labeled: Each test case should have a clear expected outcome.
  • Versioned: Track changes to your dataset over time so results remain comparable.

Here is a simple example of what an eval dataset might look like in Python:

import json

eval_dataset = [
    {
        "id": "eval-001",
        "input": "What is the capital of France?",
        "expected_output": "Paris",
        "category": "factual"
    },
    {
        "id": "eval-002",
        "input": "Summarize the latest news about climate change.",
        "expected_tools": ["web_search"],
        "expected_contains": ["climate", "change"],
        "category": "tool_use"
    },
    {
        "id": "eval-003",
        "input": "Tell me a joke about programming.",
        "category": "creative",
        "min_length": 20
    }
]

# Save to a JSON file for reuse
with open("eval_dataset.json", "w") as f:
    json.dump(eval_dataset, f, indent=2)

print(f"Created eval dataset with {len(eval_dataset)} test cases.")
Warning: Never train your agent on your eval dataset. If your test cases leak into training data, your evaluation results will be artificially inflated and meaningless. Always keep eval data strictly separate from training data.

Metrics: How to Score Your Agent

Once you have a dataset, you need metrics to quantify performance. Different tasks call for different metrics.

Common Evaluation Metrics

Metric What It Measures Best For Example
Exact Match (EM) Does the output match the expected answer exactly? Factual Q&A "Paris" == "Paris" → 1, "paris" == "Paris" → 0
F1 Score Overlap between predicted and expected tokens Span extraction Partial credit for partially correct answers
Tool Accuracy Did the agent call the correct tool(s)? Tool-use agents 3 out of 4 correct tool calls → 75%
Pass@k Probability of at least one correct answer in k tries Reasoning tasks Pass@1 = single attempt accuracy
Human Rating (1–5) Subjective quality judged by a human Open-ended generation Average rating across multiple evaluators
Latency (ms) Time from input to output Performance-sensitive apps p50, p95, p99 response times

Writing Evaluation Code

Let us build a simple evaluation runner in Python. This script will load your eval dataset, run each test case through your agent, and compute basic metrics.

import json
import time

def run_agent(input_text):
    """
    Placeholder for your actual agent function.
    In practice, this calls your LLM agent with the input
    and returns the agent's response along with tool calls.
    """
    # Simulate agent response
    response = f"Response to: {input_text}"
    tools_called = ["web_search"]  # simulated tool calls
    return response, tools_called

def evaluate_agent(eval_dataset):
    results = []
    total_cases = len(eval_dataset)
    exact_matches = 0
    tool_correct = 0
    total_latency = 0

    for case in eval_dataset:
        start_time = time.time()

        # Run the agent
        response, tools_called = run_agent(case["input"])

        # Measure latency
        latency = (time.time() - start_time) * 1000  # convert to ms
        total_latency += latency

        # Check exact match
        passed = False
        if "expected_output" in case:
            passed = response.strip() == case["expected_output"].strip()
            if passed:
                exact_matches += 1

        # Check tool accuracy
        if "expected_tools" in case:
            expected = set(case["expected_tools"])
            actual = set(tools_called)
            if expected == actual:
                tool_correct += 1

        results.append({
            "id": case["id"],
            "passed": passed,
            "latency_ms": round(latency, 2)
        })

    # Compute aggregate metrics
    avg_latency = total_latency / total_cases
    em_score = (exact_matches / total_cases) * 100

    print("=" * 50)
    print(f"Evaluation Results ({total_cases} test cases)")
    print("=" * 50)
    print(f"Exact Match Score:  {em_score:.1f}%")
    print(f"Tool Accuracy:      {tool_correct}/{total_cases}")
    print(f"Avg Latency:        {avg_latency:.0f} ms")
    print("=" * 50)

    return results

# Load dataset and run evaluation
with open("eval_dataset.json") as f:
    dataset = json.load(f)

results = evaluate_agent(dataset)

# Save results
with open("eval_results.json", "w") as f:
    json.dump(results, f, indent=2)

print("Results saved to eval_results.json")

Understanding the Code

Here is what each section does:

  • run_agent(): A placeholder function representing your actual agent. In a real project, this is where you would invoke your LLM with the appropriate prompt and tools.
  • evaluate_agent(): Loops through every test case, runs the agent, measures latency, and checks whether the output matches expectations.
  • Metrics computation: After all test cases are run, it calculates the exact match score, tool accuracy, and average latency.
  • Results persistence: Saves the results to a JSON file so you can track performance over time.
Scaling Tip: For large eval datasets, use concurrent.futures.ThreadPoolExecutor to run test cases in parallel. This can cut evaluation time dramatically — from hours to minutes.

Building an Eval Pipeline

A single evaluation run is useful, but a pipeline that runs automatically is far more powerful. An eval pipeline is a repeatable process that evaluates your agent every time you make a change.

Stages of an Eval Pipeline

  1. Trigger: The pipeline starts when you push new code, update a prompt, or on a scheduled basis (e.g., nightly).
  2. Setup: Load the eval dataset, configure the agent, and initialize any tools or APIs needed.
  3. Execution: Run all test cases against the agent. Log every input, output, and tool call for debugging.
  4. Scoring: Compute metrics and compare them against baseline thresholds.
  5. Reporting: Generate a summary report. Flag any regressions or failures.
  6. Gate: If the agent fails critical tests, block the deployment until issues are fixed.
# Example: A minimal eval pipeline using a configuration file

pipeline_config = {
    "name": "agent-daily-eval",
    "trigger": "nightly",
    "dataset": "eval_dataset.json",
    "thresholds": {
        "exact_match_min": 80.0,
        "tool_accuracy_min": 90.0,
        "max_avg_latency_ms": 2000
    },
    "notifications": {
        "on_failure": ["team-slack-channel"],
        "on_success": ["log_only"]
    }
}

def run_pipeline(config):
    print(f"Starting pipeline: {config['name']}")

    # Load dataset
    with open(config["dataset"]) as f:
        dataset = json.load(f)

    # Run evaluation
    results = evaluate_agent(dataset)  # reuse our function from above

    # Check thresholds
    thresholds = config["thresholds"]
    failures = []

    pass_rate = sum(1 for r in results if r["passed"]) / len(results) * 100
    if pass_rate < thresholds["exact_match_min"]:
        failures.append(f"Exact match {pass_rate:.1f}% < {thresholds['exact_match_min']}%")

    if failures:
        print("PIPELINE FAILED:")
        for f in failures:
            print(f"  - {f}")
        print("Sending failure notification...")
    else:
        print("Pipeline passed. No regressions detected.")

run_pipeline(pipeline_config)
Important: Always set baseline thresholds before you start iterating. If you set thresholds after seeing results, you risk tuning them to pass rather than setting meaningful quality bars.

Coding Exercise

Exercise

Write a Python function called score_tool_use that takes an expected_tools list and an actual_tools list, and returns a precision, recall, and F1 score for the agent's tool-calling behavior.

Requirements:

  • Precision = (correct tools called) / (total tools called)
  • Recall = (correct tools called) / (total tools expected)
  • F1 = 2 * (precision * recall) / (precision + recall)
  • Handle edge cases where lists might be empty.

Test it with: expected = ["web_search", "calculator"], actual = ["web_search", "calculator", "web_search"]

def score_tool_use(expected_tools, actual_tools):
    """
    Calculate precision, recall, and F1 for tool use.

    Args:
        expected_tools: list of tool names the agent should have called
        actual_tools: list of tool names the agent actually called

    Returns:
        dict with 'precision', 'recall', and 'f1' scores
    """
    # Convert to sets for comparison (duplicates don't count)
    expected_set = set(expected_tools)
    actual_set = set(actual_tools)

    # Correct tools = intersection of expected and actual
    correct_tools = expected_set & actual_set

    # Precision: out of all tools called, how many were correct?
    if len(actual_set) == 0:
        precision = 0.0
    else:
        precision = len(correct_tools) / len(actual_set)

    # Recall: out of all expected tools, how many did we call?
    if len(expected_set) == 0:
        recall = 0.0
    else:
        recall = len(correct_tools) / len(expected_set)

    # F1: harmonic mean of precision and recall
    if precision + recall == 0:
        f1 = 0.0
    else:
        f1 = 2 * (precision * recall) / (precision + recall)

    return {
        "precision": round(precision, 2),
        "recall": round(recall, 2),
        "f1": round(f1, 2)
    }

# Test the function
expected = ["web_search", "calculator"]
actual = ["web_search", "calculator", "web_search"]

result = score_tool_use(expected, actual)
print(f"Precision: {result['precision']}")  # 1.0 (both unique tools correct)
print(f"Recall:    {result['recall']}")     # 1.0 (all expected tools found)
print(f"F1:        {result['f1']}")         # 1.0 (perfect score)

Explanation: Even though "web_search" appears twice in the actual calls, we use sets to deduplicate, so the agent correctly called both expected tools. Precision is 1.0 because both unique tools it called were needed. Recall is 1.0 because it found every expected tool. This gives a perfect F1 of 1.0.

Common Pitfalls in Evaluation

Even experienced developers make mistakes when building evaluations. Here are the most common pitfalls to watch out for:

  • Data leakage: Accidentally including eval test cases in your training or fine-tuning data. Always separate datasets strictly.
  • Overfitting to evals: Optimizing your agent specifically to pass your test cases rather than genuinely improving quality. This is called "teaching to the test."
  • Insufficient coverage: Only testing happy-path scenarios. Make sure your eval dataset includes adversarial inputs, edge cases, and ambiguous queries.
  • Ignoring latency: An agent that is accurate but takes 30 seconds to respond is not production-worthy. Always measure and set thresholds for response time.
  • Static eval sets: User behavior evolves over time. Refresh your eval dataset periodically to reflect new use cases and patterns.
Remember: Evaluations are not a one-time activity. They are a continuous practice. The best teams run evals on every code change and review results as a team.

Key Takeaways

  • Evaluations provide objective, repeatable measurements of your AI agent's quality — they are essential, not optional.
  • There are four main types of evaluations: unit, integration, end-to-end, and human. Each serves a different purpose and stage of development.
  • A good eval dataset is representative, diverse, labeled, and versioned. Never let eval data leak into training data.
  • Choose metrics that match your task: exact match for factual Q&A, tool accuracy for tool-use agents, human ratings for subjective outputs, and latency for performance.
  • An eval pipeline automates the process — triggering on code changes, running tests, scoring results, and blocking deployments if quality drops.
  • Watch out for common pitfalls like data leakage, overfitting to evals, insufficient coverage, and ignoring latency.
  • Evaluation is a continuous practice that should grow and evolve alongside your agent.
